# Try-Catch Architecture Update & Refactoring Plan

## 1. Context & User Request
The user wants to implement a robust `try-catch-finally` system in an ARC (Automatic Reference Counting) environment WITHOUT relying solely on dynamic exception unwinding tables mapping.
Instead, we will rely on **"Cleanup Blocks" (brackets/scopes)**. 
- Every `{}` (block) is assigned a specific cleanup segment generated by the Assembler.
- When an exception is thrown, execution immediately jumps to the innermost block's cleanup code.
- Normal `{}` cleanup segments will decrement reference counts for local variables and then **jump to the outer scope's cleanup segment**.
- Function `{}` cleanup segments will decrement locals, pop the current `Frame` (unwinding the call stack), read the old `return_ip`, determine which block that `return_ip` belonged to, and jump to that block's cleanup segment in the caller frame.
- Try `{}` cleanup segments will clean up their locals and then **jump to the corresponding `catch` evaluation code**.

## 2. Updated Implementation Strategy

### Phase 1: Re-Parsing & AST Tagging
- Add an `enum class BlockKind { NORMAL, FUNCTION_BODY, TRY_BODY }` to `statements.hpp`.
- Modify `BlockStatement` to store its `BlockKind`.
- Modify the `Parser` to properly tag `try { ... }` blocks as `TRY_BODY`, function bodies as `FUNCTION_BODY`, and normal `{ ... }` as `NORMAL`.
- **Commit Phase 1**

### Phase 2: Binder Updates
- Update the Binder to process `TryStatement`, `CatchClause`, and `ThrowStatement` correctly.
- Add `catch_param_decl` to `CatchClause` explicitly inside `statements.hpp`. Ensure its declaration works like a normal local variable (so `resolve` can find it) and avoids pointer dangling or memory corruption.
- Specifically fix `evaluate_expression` and `bind_node` so that `current_pass` does not leak between AST nodes. (This was the root cause of our previous failures!)
- **Commit Phase 2**

### Phase 3: Runtime Unwinding Support & OpCodes
- Add new opcodes:
  - `REGISTER_CLEANUP_BLOCK`: Registers a mapping `(start_ip, end_ip) -> cleanup_ip`.
  - `THROW_EXCEPTION`: Halts normal execution, finds the innermost cleanup block for the current `program_counter`, and jumps to it. If none is found, it looks at `return_ip` and pops frames until it finds a handler.
  - `JUMP_TO_OUTER_CLEANUP`: At the end of a cleanup block, this opcode determines the next outer block (or pops the frame) and jumps to it.
  - `GET_EXCEPTION`: Retrieves the currently active exception object.
  - `CLEAR_EXCEPTION`: Clears the active exception once caught.
- Add `active_exception` address to `RuntimeContext`.
- Add a lightweight lookup table in `RuntimeContext` for the currently registered blocks, updated dynamically during execution OR parsed at load-time from a side-table. Wait, the user said: "with my idea we dont need no table at all. when we throw we just jump to bracket clenup...".
  - If we don't use a table for local jumps, `THROW` could just fetch a dynamically managed "current_cleanup_handler" address pushed to a handler stack?
  - But wait! For cross-function unwinding, the user said: "function {}, also gonna cleanup the variable code but then will check were it was suppose to jump back (oh yeah we are gonna need an table so that it know if i was supose to jump here after this function that mean i must jump to this cleanup bracket segment code)".
  - So we DO need a table that maps `return_ip -> cleanup_ip`.
- **Commit Phase 3**

### Phase 4: Assembler Generation
- In `Assembler::visit(BlockStatement)`, emit the logic:
  - Normal execution.
  - Jump over cleanup.
  - Cleanup segment (decrements references).
  - Jump to outer cleanup.
- In `Assembler::visit(TryStatement)`, emit Try block. Its cleanup segment jumps to Catch matching logic.
- **Commit Phase 4**
